# Xyvora platform upgrade: staging and activation

This branch adds working upgrade slices to the existing app. It is not a production deployment, and a connected Arena app does not configure a runtime provider.

## What's in this branch

- Private projects: name, description, icon, color and instructions; project-scoped conversations and a reference library. Drag/drop or browse to upload extracts from text/code/CSV/JSON/Markdown, readable PDFs, DOCX, or XLSX. Read and delete file extracts. Project chat can retrieve up to three keyword-ranked excerpts. Personal memory is not sent from a project; temporary or isolated messages do not use project context. Guest chat stays separate.
- Normalized conversations: per-conversation revisions, indexed paging, on-demand bodies and full-text search across stored titles and messages. Limits are 5,000 chats, 120 turns per chat, 64 MB per account, and a bounded request size per chat. Older conversations and branches migrate without changing their IDs. Search groups results, with separate chat, message, project, file, action, favorite and archive filters. Rename, pin, favorite, archive/restore, duplicate, move between projects, export and delete work in the UI.
- Account options: opt-in Supabase Auth for Google/GitHub PKCE and email verification/recovery. Xyvora stores app sessions, not provider access/refresh tokens. List and revoke active app sessions. Legacy password and OAuth accounts remain usable if enabled.
- Models: Xyvora remains the default. Signed-in users can explicitly select a configured OpenAI, Anthropic, Gemini or operator-owned OpenAI-compatible text endpoint. `Auto` uses Xyvora for Normal/Instant and a configured hosted model for the higher-effort modes or research. On a hosted failure, `Auto` can fall back to Xyvora only before text starts. It never tries another hosted vendor with the same context. External replies identify the configured provider/model. Only text streaming is supported by these adapters; no tool calls are executed on provider instructions.
- Research: `/research QUERY` or **Research brief** in the command palette. Wiby and Wikipedia search receive only the query. For matching Wikipedia results, the server requests the opening text from the publisher's TextExtracts API. Cards distinguish retrieved introductions from index snippets. Wiby links are not fetched. A brief uses numbered evidence, not live news, image search, full page crawls, or an exhaustive literature search.
- Appearance and replies: locally stored guest or synced account accent, spacing, text size and font; existing light/dark themes and Orbit animation. Markdown now has selectable tables, lazy syntax coloring, per-block copy and a bounded, data-only Mermaid flowchart subset (`TD`, `TB`, `LR`, box labels and simple arrows, no cycles/directives/HTML). Unsupported diagrams remain copyable source.

**File boundary:** The browser reads at most 4 MB per upload and saves at most 8,000 characters of text per file in each project. Office parsing is bounded; Word formatting and Excel recalculation are not supported. Excel previews show up to three sheets, cached cell values and raw numbers, not rendered styles or formulas. Scanned PDFs need OCR first. Project deletion removes file extracts and detaches chats; previous replies that quoted a file are part of the chat until you delete that chat. Original binaries and image libraries are not stored. There are no public file buckets or share links.

## Staging first

1. Back up the target database and rehearse on disposable staging. [Configure the scoped PostgreSQL connection](supabase-setup.md) with verified TLS. Do not use a database owner or broadly privileged `postgres` URL in the app.
2. Apply the existing migrations `001`–`003`, then [004_projects.sql](../database/004_projects.sql), [005_conversation_library.sql](../database/005_conversation_library.sql), and [006_session_management.sql](../database/006_session_management.sql), in order. Use PostgreSQL 15+ (the chat-to-project FK uses column-specific `ON DELETE SET NULL`). Verify `xyvora_app` is not `BYPASSRLS` and Data API roles (`anon`, `authenticated`, `service_role`) and `xyvora_worker` cannot access the new project/library tables. New rows require a transaction-bound account scope derived only from the verified app session, plus explicit owner-qualified queries. The old tables still use server-role RLS and app authorization, not browser policies based on `auth.uid()`.
3. Deploy the **code to protected staging** before enabling `XYVORA_ENABLE_PROJECTS=1`, `XYVORA_ENABLE_LIBRARY=1`, and `XYVORA_ENABLE_SESSIONS=1` there. Nothing in the migration enables a production flag. Test with independent accounts and browsers. Verify temporary, guest and inactive-account data do not appear in project lookup, previews or search. Set `XYVORA_ENABLE_RESEARCH=1` separately after verifying the outbound publisher responses from staging.
4. Library cutover happens lazily on the first new library request for each account. The server locks the old revision row, imports the validated snapshot, and freezes the old row in one transaction. Old clients get a reload error. Migrated JSON is emptied only when import succeeds, not retained as a duplicate of conversations the user may later delete. **Do not switch an already migrated account back to legacy mode** or roll it onto code that cannot read the library. The prior library-capable build is the safe rollback target after cutover. Restoring a pre-cutover DB snapshot loses newer changes; do that only as an explicit incident recovery with accounting for current data. Original guest and old browser-scoped history remain unaffected.
5. The production build is `npm run build`, then `npm run check:site`. The standard Vercel release also needs `npm run build:models` and the [launch runbook](launch-runbook.md). Confirm the native model and actual search from a protected Vercel preview before promoting. Rotate/delete disposable credentials and accounts when finished. Do not add keys to Git, client variables, screenshots, or chats.

## Activate Supabase Auth

1. Use a **dedicated** Supabase Auth project (do not use a project with unrelated app users). Keep the Postgres runtime credentials independent. Set `XYVORA_ACCOUNT_ORIGIN` to the exact HTTPS app origin. In Supabase Auth URL Configuration add exactly `<account-origin>/api/account?auth=supabase` as an allowed redirect, with the app's own origin as Site URL. Do not allow arbitrary preview origins. In each Google/GitHub provider dashboard use `https://<project-ref>.supabase.co/auth/v1/callback` as Supabase's redirect target; enable only providers that are configured in both dashboards.
2. Enable `XYVORA_ENABLE_SUPABASE_AUTH=1` and set `XYVORA_SUPABASE_AUTH_URL`, `XYVORA_SUPABASE_PUBLISHABLE_KEY`, `XYVORA_SUPABASE_ADMIN_KEY`, `XYVORA_AUTH_SECRET`, and the approved names in `XYVORA_SUPABASE_AUTH_PROVIDERS`. Use Vercel Sensitive server variables for keys. The server-only Auth admin key is needed to delete linked Auth users on request; it is never used for conversation storage. Restrict its environment and rotate it separately. It is a powerful credential; do not point this release at a shared Auth project.
3. Email is separate. Configure custom SMTP, require Confirm email, set a 12-character password minimum, and set Auth email OTP to **six digits** expiring in at most **10 minutes**. In both **Confirm signup** and **Reset password** templates send `{{ .Token }}` as a code, not a confirmation link. Set an appropriate provider email send rate and review Auth security settings before enabling `XYVORA_SUPABASE_EMAIL_AUTH=1`. Test actual mail delivery, verification, login, reset and immediate Xyvora session revocation, then delete a disposable user and verify deletion in **both** stores. The local mail catcher only tests legacy auth; it does not stand in for Supabase SMTP.
4. Supabase identities are keyed by project issuer and verified Auth UUID. Identical email addresses do **not** attach to a prior Xyvora account or its data. Keep the existing sign-in paths configured for legacy users. In the sign-in dialog, **Use existing Xyvora sign-in** reaches those accounts. Coordinated identity linking/import is not in this release; do not disable the old sign-in for a project with active legacy users. Account deletion of a Supabase-authenticated identity still requires the original Auth project and its admin key.

## Activate hosted inference

1. Set server variables from [`.env.example`](../.env.example), including `XYVORA_ENABLE_HOSTED_MODELS=1`, `XYVORA_AUTH_SECRET`, and the provider's exact model ID and key. For a compatible endpoint, use a trusted, operator-controlled public TLS hostname and full `/chat/completions` URL. Requests cannot set the destination. Redirects are rejected.
2. Reserve hard spend limits in the vendor projects; set the per-account and per-site daily request caps. The app charges a request to the budget before each hosted attempt, even if the vendor fails; counters contain no prompt text. Guests cannot select or call these routes. A named provider choice does not silently fall back. If consent to send data changes, switch the text model back to Xyvora; new or reopened chats default to Xyvora.
3. Use a disposable account to verify an actual streamed reply and cancellation for each configured vendor, the model badge, a budget refusal, Auto fallback and provider failure. Verify the disclosure accurately reflects data sent: current prompt, included recent chat/attachment text, project excerpts or enabled notes, and available evidence. Avoid sensitive prompt data in provider testing.

## Still open before calling the 100× upgrade complete

The paused plugin API and Zapier staging are not changed by this upgrade.
