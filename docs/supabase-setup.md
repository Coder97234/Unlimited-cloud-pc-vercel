# Use Supabase for Xyvora accounts

Use Supabase as **hosted PostgreSQL**, not as a second sign-in system. Xyvora still handles passwords, email verification/recovery, OAuth sign-in and account cookies. Chat history, preferences, notes, analytics and jobs use the same database. No Supabase client, anon key or service-role key is needed in the browser or on Vercel.

1. Pick a dedicated Supabase project for Xyvora. Take a backup if it has existing Xyvora data. Test against a separate staging project before migrating production. In a dedicated project, disable the Data API before applying migrations if you don't need it. Don't disable a shared project's API for other apps.
2. As the database owner, run [`001_platform.sql`](../database/001_platform.sql), [`002_launch.sql`](../database/002_launch.sql) and [`003_server_access.sql`](../database/003_server_access.sql), in that order. On an already migrated release, apply only the pending migration. The last migration enables row-level security and revokes `anon`, `authenticated`, `service_role` and `PUBLIC` access **only** on Xyvora's tables. It creates `xyvora_app` and `xyvora_worker` without a login by default. Keep these roles dedicated to this app; don't grant them to other roles or use the database admin for the website.
3. Set distinct strong passwords using your own administrator `psql` session (`\password xyvora_app`; then `ALTER ROLE xyvora_app LOGIN;`). Do the equivalent for `xyvora_worker` only if you will run the worker. Use a secure prompt and a TLS connection. Don't put passwords in the SQL editor, committed migrations, screenshots, chat, or command arguments.
4. In Supabase's **Connect** panel, copy the server connection settings. Use the **Transaction pooler** (typically port 6543) for Vercel, with username `xyvora_app.<project-ref>` rather than `postgres.<project-ref>` on the shared pooler. Use `xyvora_worker` on a verified-TLS direct connection, or `xyvora_worker.<project-ref>` through the **Session pooler** if a persistent worker cannot reach the direct endpoint. Use your real pooler hostname, percent-encode the password in the connection URL, and use certificate verification (`sslmode=verify-full`, with the appropriate CA trusted by your runtime). Xyvora sends no named prepared statements and limits each warm Supabase pool to one connection. See [Supabase's connection guide](https://supabase.com/docs/guides/database/connecting-to-postgres).
5. Store the scoped connection in `XYVORA_DATABASE_URL` as a **sensitive server variable** in the Vercel project's matching environment. The worker gets its own connection in its own runtime variables. Use the same exact `XYVORA_ACCOUNT_ORIGIN` as the selected app domain. Do not use a `VITE_` prefix. To add email accounts, configure a [Bird mailbox](bird-setup.md) for codes or Resend for links, and the password variables in the [launch runbook](launch-runbook.md#2-enable-email-and-social-sign-in). Xyvora does not use the Supabase Auth email sender. Social sign-in and private plugins require their own credentials and grants. Redeploy after changing variables.
6. In protected staging, verify the database user is `xyvora_app` (not `postgres`); create a test account, open the verification email, sign in from two browsers, sync a chat and settings, check password reset and delete the test account. Check that the Supabase Data API cannot read or write the Xyvora tables. Apply the [worker and retention checks](launch-runbook.md#3-run-the-durable-text-queue) if you enable those features.

For help choosing the project, share only the **project name or reference** and whether you are using a new or existing database. Add actual credentials directly to the provider dashboards. Arena's Supabase connector and Vercel/Gmail connections aren't website credentials.
